Control de acceso por tarjetas RFID para obras de construcción

Un trabajador acerca su tarjeta al lector de una zona. El sistema decide si puede entrar, guarda el registro, detecta comportamientos sospechosos y genera reportes en PDF. Es un proyecto en Java 21 hecho como reto de Programación Orientada a Objetos.

01 Qué hace el sistema

En una obra hay zonas con distinto nivel de riesgo. Cada trabajador tiene una tarjeta y un nivel de acceso, y en la puerta de cada zona hay un lector.

1

Identifica la tarjeta

Calcula el hash SHA-256 del UID. El código real de la tarjeta nunca se guarda.

2

Decide el acceso

Revisa si la tarjeta existe, si está activa y si el nivel del trabajador alcanza el de la zona.

3

Registra el intento

Guarda cada intento, exitoso o no, con el motivo exacto si se negó.

4

Detecta anomalías

Genera alertas por tarjeta desconocida, tarjeta bloqueada, intentos repetidos y accesos fuera de horario.

5

Genera reportes

Crea un PDF con el resumen, el historial de accesos y las alertas.

6

Sin hardware

Un lector simulado permite probar todo desde la ventana o la consola.

Alertas que detecta

AlertaCuándo se dispara
TARJETA_DESCONOCIDASe usa una tarjeta que no está registrada.
TARJETA_INACTIVASe usa una tarjeta bloqueada (por ejemplo, reportada como perdida).
INTENTOS_REPETIDOSHay 3 o más accesos denegados con la misma tarjeta en 5 minutos.
FUERA_DE_HORARIOSe permite un acceso fuera de la jornada (06:00–20:00). La persona entra, pero queda la alerta.

03 Cómo ejecutarlo

A · Eclipse

1. File → Import → Maven → Existing Maven Projects. Si el proyecto ya estaba importado: Maven → Update Project…

2. Abrir Main.java → Run As → Java Application.

Compila y ejecuta sin empaquetar. Es lo más cómodo mientras se desarrolla.

C · Jar ejecutable

mvn package genera un único jar con H2 y OpenPDF dentro, que se puede llevar a otra máquina con Java 21.

06 Flujo de una lectura, paso a paso

Qué pasa por dentro cuando se presiona "Pasar tarjeta".

  1. VentanaPrincipal.pasarTarjeta()
    Toma la tarjeta y la zona elegidas en los combos.
  2. SimuladorLectorRFID.simularLectura(uid, "Z-BOD", hora)
    Crea un LecturaRFID y avisa al oyente registrado.
  3. ControlAccesoService.procesarLectura(lectura)
    Busca la zona por código. Si no existe, lanza un error.
  4. CriptoService.hashUid(uid)
    Normaliza el UID (04:a3:1f:7b → 04A31F7B) y calcula su SHA-256.
  5. TarjetaRepository / TrabajadorRepository
    Busca la tarjeta por hash y su titular. Ambos devuelven Optional.
  6. evaluar(...)
    Aplica las reglas en orden; el primer "no" decide el resultado:
    ¿Existe la tarjeta? no → DENEGADO_TARJETA_DESCONOCIDA
    ¿Está activa? no → DENEGADO_TARJETA_INACTIVA
    ¿Nivel suficiente? no → DENEGADO_NIVEL_INSUFICIENTE
    Pasa todo → PERMITIDO
  7. RegistroRepository.guardar(registro)
    Inserta el registro y recupera el id generado.
  8. DetectorAnomalias.analizar(registro)
    Devuelve las alertas que correspondan, que el servicio luego guarda con AlertaRepository.
  9. VentanaPrincipal.mostrarResultado(ResultadoLectura)
    Muestra el mensaje en verde o rojo y refresca las tablas.
La consola sigue exactamente el mismo flujo; solo cambia cómo se muestra el resultado. Por eso la lógica vive en los servicios y no en la UI.

08 Archivo por archivo

Haz clic en cada paquete para ver qué hace cada clase.

Main y config · arranque y armado
Main.java

Crea AppConfig, inicializa la BD y abre la ventana Swing, o la consola si se pasó --consola o no hay pantalla. La ventana se crea con SwingUtilities.invokeLater porque Swing exige manejar toda la interfaz desde su propio hilo (el Event Dispatch Thread).

config/AppConfig.java

Es la "raíz de composición" y hace dos cosas:

  • Parámetros: URL de la BD, umbral de intentos (3), ventana de tiempo (5 min), horario laboral (06:00–20:00) y carpeta de reportes.
  • Armado: ConexionDB → repositorios → CriptoService y DetectorAnomalias → servicios → simulador.
  • Tiene un segundo constructor, AppConfig(String url), que usan los tests para trabajar con una BD limpia.
Si se cambia H2 por MySQL, PDF por CSV o el simulador por un lector real, este es el único archivo que hay que tocar.
model · el dominio
Trabajador clase

Valida en el constructor que la cédula y el nombre no estén vacíos. Contiene la regla puedeIngresarA(Zona). Dos trabajadores son iguales si tienen la misma cédula.

TarjetaRFID clase

Guarda uidHash, no el UID. Tiene bloquear() y activar(), y getHashCorto() para mostrarla en pantalla.

Zona clase

Su codigo (ej. Z-BOD) es lo que "conoce" el lector de la puerta. Su toString() se usa directamente en el combo de la ventana.

RegistroAcceso record

Inmutable. tarjetaId es null si la tarjeta era desconocida. conId() devuelve una copia con el id que asignó la BD.

Alerta record

Inmutable. Apunta al registro que la provocó (registroId).

enums/
  • Nivel: BASICO(1), RESTRINGIDO(2), CRITICO(3). Tiene alcanza(requerido). El peso es explícito para que reordenar las constantes no cambie las reglas.
  • Rol: obrero, operador, electricista, supervisor, visitante. Por ahora es solo informativo.
  • Resultado: PERMITIDO y un DENEGADO_* por cada motivo, con esPermitido().
  • TipoAlerta: uno por cada regla del detector.
reader · lectores RFID
LectorRFID interfaz

Define setOyente(Consumer<LecturaRFID>) y getNombre(). Cualquier lector, simulado o real, cumple este contrato.

LecturaRFID record

Lo que entrega el lector: el UID leído, el código de la zona y la fecha y hora.

SimuladorLectorRFID
  • UIDS_DEMO: los UIDs "impresos" en las tarjetas de demo, que coinciden con seed.sql.
  • simularLectura(uid, zona[, hora]): dispara el oyente.
  • generarUidAleatorio(): crea tarjetas desconocidas para probar.

jdbc/ConexionDB

abrir() entrega una conexión nueva en cada llamada. inicializar() ejecuta schema.sql y seed.sql.

jdbc/Jdbc*Repository

Todos siguen el mismo patrón:

try (Connection cn = conexionDB.abrir();
     PreparedStatement ps = cn.prepareStatement(SQL)) {
    ps.setString(1, valor);      // siempre "?" → evita SQL injection
    try (ResultSet rs = ps.executeQuery()) {
        ... mapear(rs) ...           // fila → objeto del modelo
    }
} catch (SQLException e) {
    throw new DatosAccesoException("mensaje", e);
}   // la conexión se cierra sola, aunque haya error
  • Los enums se guardan como texto (name()) y se leen con valueOf().
  • guardar() usa RETURN_GENERATED_KEYS para obtener el id.
  • wasNull() se consulta justo después de getLong("tarjeta_id"), porque getLong devuelve 0 cuando la columna es NULL.
jdbc/DatosAccesoException NUEVO

Envuelve la SQLException (que es checked) para que las interfaces de repositorio no queden atadas a JDBC.

service · lógica de negocio
ControlAccesoService

El corazón del sistema. procesarLectura() implementa el flujo completo. También ofrece consultas para la UI: buscarTitular, listarZonas, listarTarjetas, buscarTrabajador y alternarEstadoTarjeta.

DetectorAnomalias

Recibe un registro ya guardado y devuelve alertas, sin guardarlas. Sus parámetros (umbral, ventana, horario) llegan por constructor.

CriptoService
  • normalizarUid: acepta el UID con :, espacios o minúsculas.
  • hashUid: SHA-256 en hexadecimal (64 caracteres).
  • enmascararUid: devuelve 04:A3:**:** (todavía no se usa en la UI).
ReporteService

registrosDetallados() convierte ids en nombres cargando zonas, tarjetas y trabajadores una sola vez en mapas, lo que evita el problema N+1. generarReporte() arma un DatosReporte y lo entrega al generador inyectado.

ResultadoLectura record · NUEVO

Lo que devuelve procesarLectura: el registro, el trabajador, la zona y las alertas, más permitido() y mensaje().

report · reportes

PdfReporteGenerator

Usa OpenPDF para generar el título, el resumen, la tabla de registros (con colores) y la tabla de alertas, con encabezados que se repiten en cada página.

DatosReporte · FilaRegistro records · NUEVO

Los datos ya preparados. El generador nunca consulta la BD. FilaRegistro lo usan tanto la tabla de la ventana como el PDF.

Relaciones

  • Un trabajador puede tener varias tarjetas (1:N), por ejemplo si pierde una.
  • Un registro tiene 0 o 1 tarjeta y siempre una zona.
  • Una alerta pertenece a un registro.
  • Hay un índice en (uid_hash, fecha_hora) para contar intentos recientes.
registro_acceso.uid_hash se guarda aunque la tarjeta no exista, para poder detectar intentos repetidos de una tarjeta desconocida.

11 Decisiones de diseño (y por qué)

¿Por qué guardar el hash y no el UID?

El UID es lo que se necesita para clonar una tarjeta. Si alguien obtiene la BD, solo ve hashes. Mejora pendiente: usar HMAC-SHA256 con una clave secreta, porque los UIDs son cortos y un SHA-256 simple podría romperse por fuerza bruta.

¿Por qué una conexión nueva por operación?

Una única Connection compartida no es segura entre hilos, se puede caer y nadie sabe cuándo cerrarla. try-with-resources es el patrón estándar de JDBC; con MySQL se agregaría un pool (HikariCP) dentro de ConexionDB.

¿Por qué clases para unas cosas y record para otras?

Trabajador, Tarjeta y Zona son entidades: tienen identidad y cambian. Registro y Alerta son eventos históricos: lo que pasó no cambia.

¿Por qué varios DENEGADO_*?

Para que el historial y el reporte expliquen el motivo, y para que el detector reaccione distinto según el caso.

¿Por qué el detector no guarda las alertas?

Así tiene una sola responsabilidad (decidir) y es fácil de probar. Quién guarda y cuándo lo decide el servicio.

¿Por qué de noche se permite y solo se alerta?

Es una decisión provisional: bloquear de noche podría dejar afuera a un guardia o a una emergencia. Está entre las preguntas abiertas.

¿Por qué no Spring ni JPA?

Es un reto de POO y Java. Hacer la inyección de dependencias y el JDBC a mano demuestra que se entienden los conceptos; un framework los escondería.

12 Limitaciones de la demo

Son intencionales para mantener la demo simple, y son tareas pendientes.

  • La BD se borra al cerrar. Para persistir: jdbc:h2:./data/controlacceso y hacer que los scripts no fallen si los datos ya existen.
  • No hay alta, edición ni baja de trabajadores, zonas ni tarjetas desde la UI (solo bloquear o activar tarjetas).
  • No hay login ni usuarios del sistema.
  • Los niveles son lineales: con nivel Crítico se entra a todas las zonas críticas.
  • No se distingue entrada de salida, así que no se sabe quién está dentro.
  • El horario es el mismo todos los días (no considera fines de semana ni feriados).
  • La alerta de intentos repetidos se dispara en cada intento a partir del tercero.
  • Las consultas corren en el hilo de la UI. Con una BD remota convendría usar SwingWorker.
  • Los parámetros son constantes en AppConfig; podrían ir a un .properties.

13 Cómo extender el proyecto

Reporte CSV

1. Crear CsvReporteGenerator implements ReporteGenerator.
2. Pasarlo en AppConfig en lugar del PDF, o crear dos ReporteService con un botón cada uno.

MySQL / PostgreSQL

1. Agregar el driver al pom.xml.
2. Cambiar la URL, el usuario y la clave en AppConfig.
3. Revisar schema.sql (en PostgreSQL, AUTO_INCREMENT se escribe distinto).
Los repositorios no cambian.

Lector real (Arduino + RC522)

1. Crear LectorSerialRFID implements LectorRFID, con jSerialComm, que llame al oyente con cada UID.
2. Crearlo en AppConfig en lugar del simulador.

Nueva regla de anomalía

1. Agregar el valor a TipoAlerta.
2. Agregar el if en DetectorAnomalias.analizar().
3. Agregar un test.

CRUD de trabajadores

1. Agregar guardar, actualizar y eliminar al repositorio.
2. Crear TrabajadorService con las validaciones.
3. Agregar una pestaña nueva en la ventana.

15 Casos de uso

Qué puede hacer cada actor con el sistema. CU-01 a CU-07 están implementados en la demo; CU-08 a CU-15 son la propuesta para las siguientes iteraciones. Versión en texto: docs/CASOS_DE_USO.md.

Actores

Trabajador

Pasa la tarjeta para entrar a una zona.

Lector RFID sistema

Lee el UID en la puerta y lo envía. En la demo es SimuladorLectorRFID.

Guardia

Vigila los accesos y las alertas en tiempo real.

Supervisor

Revisa el historial y genera reportes.

Administrador

Gestiona tarjetas, trabajadores, zonas y la configuración.

La demo no tiene login, así que quien la abre actúa como guardia, supervisor y administrador a la vez.

Implementados

CU-01 Solicitar acceso a una zona · Trabajador, Lector RFID · «include» CU-02
ObjetivoQue el trabajador entre a una zona si tiene permiso.
PrecondiciónLa zona existe y su lector funciona.
PostcondiciónQueda el registro (CU-02) y, si corresponde, alertas (CU-03).
ReglasRN-01, RN-02, RN-03, RN-04, RN-06
Flujo principal
  1. El trabajador acerca su tarjeta al lector de la zona.
  2. El lector envía una LecturaRFID (UID, zona, hora).
  3. El sistema busca la zona por su código.
  4. Calcula el hash del UID.
  5. Busca la tarjeta por hash y a su titular.
  6. Verifica que la tarjeta esté activa.
  7. Verifica que el nivel del trabajador alcance el de la zona.
  8. Resultado PERMITIDO.
  9. Incluye CU-02 (registrar el intento).
  10. Muestra el resultado en verde.
Flujos alternativos
  • 3a La zona no existe: Error; no se registra nada.
  • 4a UID sin caracteres hexadecimales: Error "UID inválido"; no se registra.
  • 5a La tarjeta no existe: DENEGADO_TARJETA_DESCONOCIDA → paso 9, en rojo.
  • 6a Tarjeta bloqueada: DENEGADO_TARJETA_INACTIVA → paso 9.
  • 7a Nivel insuficiente: DENEGADO_NIVEL_INSUFICIENTE → paso 9.

CU-03 Detectar anomalías y generar alertas · (sistema); las ve el Guardia · «extend» CU-02
ObjetivoAvisar de situaciones sospechosas, aunque no siempre impliquen negar el acceso.
PrecondiciónEl registro ya está guardado y tiene id.
PostcondiciónCero o más alertas guardadas, enlazadas al registro.
ReglasRN-07, RN-08, RN-09
Flujo principal
  1. Analiza el registro recién guardado.
  2. Tarjeta desconocida → alerta TARJETA_DESCONOCIDA.
  3. Tarjeta bloqueada → alerta TARJETA_INACTIVA.
  4. Si fue denegado: cuenta los denegados del hash en 5 min; si son 3 o más → INTENTOS_REPETIDOS.
  5. Si fue permitido fuera de 06:00–20:00 → FUERA_DE_HORARIO.
  6. Guarda cada alerta y la devuelve a la UI.
Flujos alternativos

No tiene. Un mismo intento puede generar varias alertas.
